# GPU / 性能剖析系列 · 写作规范

这份文件是 **GPU 与性能剖析系列**的体例来源,和面试算法系列的
`CONVENTIONS.md` **并列,不是它的子集**。

两个系列共享的只有工具(`_tools/svgkit.py`、`verify_post.py`、`verify_svg.py`)
和仓库层面的排版约定;下面第 1、4、5、6 节讲的是 GPU 系列**必须不一样**的地方。

写这个系列的文章之前先读这份;写完跑第 7 节四道门。

---

## 1 定位与出处(和算法系列最大的区别)

算法系列的材料是教程,结论是**确定**的(复杂度、边界条件),风险在于抄。
GPU 系列的材料是**别人报的性能数字**,结论是**可测量的**,风险完全不同:

**材料方报的数字,一律当成「待验证的断言」,不是当成事实。**

这是这个系列存在的理由。一份性能演讲里出现的每个倍数,都隐含了一组
硬件、一个规模、一种测法;这三样没对齐,数字就不能搬。所以:

**必须做到的:**

- 引用别人的性能数字时,**同时写出它的出处和它的适用条件**
- **每个性能实验至少跑两遍**,并且把两遍都写进文章(见第 5.7 节)。
  这条不是形式要求:本规范的第一次实践里,复跑否掉了一条已经写好的结论
  (一个 +34.8%,复跑只有 +5.2%)
- 自己实测之后,**明确区分**三种情况:
  1. 我测出来和它一致 → 写「复现了」
  2. 我测出来比它高/低 → 写清差多少,并给出**可能的**原因(硬件代差、
     规模不同、测法不同)。用「大概」「可能是」,不要断言对方错
  3. 我测不出来(缺硬件、缺材料) → 写「没验证」,**不要**改写成「据称」
- **每个数字都要写清「到底哪个变量变了」。** 一个性能对比如果同时改了两
  个东西,它就不能被复现,也不能被移植——这种实验要么拆成两步,要么不写

**绝对不可以:**

- 把「我把两个变量一起改了」测出的倍数,归因给其中一个变量
- 声称跑过没跑过的实验;**编造性能数字比算法系列严重得多**,因为算法
  结论错了读者能推出来,性能数字错了没人能发现
- 只给倍数不给环境(H800?V100?什么规模?几次取平均?)
- **只报对自己结论有利的那一遍。** 两遍都列出来,哪怕其中一遍更难看

**关于硬件:** 这个系列默认在真实 GPU 上跑(`nvcc` + `nsys`),不是模拟。
跑不了就明说「这一节没有实测」。

和算法系列一致:

```text
  verify_code.py  代码门:抽正文代码真跑 + 核数字
  *.cu, *.sh, *.sbatch
```

```markdown
## 0 先说明材料和我的写法

(材料出处 + 链接;**明确写出这份材料的可用程度**
 —— 文字层能抽多少、哪些内容在图片里拿不到 + 我的实测环境)

### 目录
- [0 ...](#...)
...

## 1 <材料讲了什么>(整理,标注哪些是文字层事实)

## 2 <复现的核心发现>(这部分必须是自己的实测)

## ...

## N 把结论收成一张表
## N+1 2018 到今天(时间对照,见第 6 节)
## N+2 材料与出处(含「哪些是我的判断」)
```

**硬性要求:**

- 编号从 0 开始,每个 `##` 标题都要在 `### 目录` 里有一条链接。
  锚点算法同算法系列(见 `CONVENTIONS.md` 第 4 节)
- 标题里**不要出现 `µ`、`×`、`√` 这类字符** —— `verify_post.py` 会拦。
  微秒写「微秒」或 `us`,乘号写 `x`。原因是这类字符在本地与线上生成的
  锚点 id 会不一致
- 标题里的 `:` 用半角,锚点里没有它

**这个系列的特色(每篇都要有):**

1. **一个「忙 vs 等」的量化。** GPU 文章的立身之本是**区分「GPU 在算」
   和「GPU 在等」**。任何一篇都要给出这个拆分,不能只给总时间
2. **一个恒等式。** 例:`总跨度 = 在算 + 空隙 + 尾`。恒等式是自查手段 ——
   它不成立就说明解析或测量写错了
3. **一段「哪些是我自己的判断」。** 出处那一节要有,逐条列。哪些数是
   实测、哪些是实测之上的推断、哪些没验证
4. **一个「怎么做错的」。** 见第 5 节
5. 结尾一张**归纳表**:反模式 / 我实测的代价 / 材料里的说法 / 适用条件。
   「适用条件」这一列不能空

## 5 数字纪律(这个系列的核心)

### 5.1 正文的数字必须是脚本重算出来的,不能手抄

**规则:正文和插图里出现的每一个数,都要能由一个脚本从原始数据重算。**

```python
# nsight_data.py —— 正文数字的唯一来源
DATA = HERE / "data"
def wallclock(): ...   # 解析 data/run_<jobid>.log
def gaps(): ...        # 解析 data/trace_*.csv
```

`verify_code.py` 里放一张 `{正文里的数: 实测值}` 的对照表,逐项比对。
「改了实验忘了改正文」是这个系列最常见、也最难肉眼发现的错误。

### 5.2 归一化用精确值,不要用已经四舍五入的值

真实踩过的坑:先算出 `1.9091` 显示成 `1.91`,另一个地方拿 `1.91` 去
继续算,结果和 `1.92` 对不上。**中间量一律保留完整精度,只在打印时
格式化。** 显示倍数的 `%.1f` / `%.2f` 要全文统一。

### 5.3 性能对比的实验设计:一次只动一个变量

这是第 1 节那条规矩的操作版本。真实踩过的坑:同一份实验里
「同步 `cudaMemcpy` → 零拷贝」比出了 **332.5%**,而材料里说 20%。
看起来是重大发现,实际上**同时改了两个东西**(阻塞 → 不阻塞、
设备内存 → 主机内存),测出来的主要是前者。

修法不是重测,是**加一条中间路径**,让每一步只变一个变量:

```text
A: 同步拷贝             ┐
C: 异步 + 固定主机内存   ├ A→C 只变「异步」  = 22.4%
B: 零拷贝(映射内存)     ┘ C→B 只变「零拷贝」 = 295.0%
```

**判据:一个性能对比如果在两个维度上都不同,它没有结论。**

### 5.4 对照组必须做同一件事

制造性能差异的办法绝不能是「让对照组少算」。跑完要有一次**结果一致性
校验**,并且把它写进文章:

```text
五种模式的 checksum 全部 = -174.535   ← 这才叫「算的是同一件事」
```

真实踩过的坑:为了模拟「每轮重新分配」而每轮新建了累加器,新的是零,
等于把累加清零了,checksum 从 `-34927` 变成 `-174.535`,和其他模式对不上。
**是我的 bug,不是「分配慢」的证据。**

### 5.5 「测到的是固定开销」的三个症状

- 几组不同参数的输出**几乎逐位相同** → 自变量根本没进到被测区间
- 绝对值小到和启动开销同量级(几十微秒级) → 倍数没有意义,要说明
- 单次采样就下结论 → 见 5.7 节,至少跑两遍

真实踩过的坑:`batch = 4 / 16 / 64` 三行给出完全相同的 `0.143 ms`,
看起来「很稳定」,实际测的是固定开销。**加工作量能解决「数值分不开」,
但不一定能解决「测的不是那个东西」** —— 前者靠调参数,后者只能靠复跑。

判断哪一侧撞了地板,办法很简单:**把「应该随参数变化」的那一列单独看。**
某一列在参数变 4 倍、16 倍、64 倍时纹丝不动,那一侧就不该拿来比。

### 5.6 慢就是慢,不要替它找借口

失败、死锁、慢得离谱,都要照实写。**而且要先怀疑自己的实验设计,
再怀疑被测对象。** 真实踩过的坑:测出每次 `pthread_cond_broadcast`
要 2.6 ms,而材料说 60 µs,差四十多倍。最后查明是我的实验在**任务粒度**
上做同步,而材料的数字是**屏障粒度** —— 两边根本不是同一件事。

**排查过程中得到的数字,和写进文章的结论,是两个不同性质的东西。**
那个 2.6 ms 的探针数字帮我定位了方向,但它本身不可引用:探针里没有实际
工作,线程被唤醒后立刻回到等待,人为造出了最坏的护航效应。换台机器、
换个线程数就变。**能引用的只有受控对比里的差值。**

### 5.7 至少跑两遍,而且两遍都要写

这是这个系列最贵、也最值钱的一条规矩。

**实测教训:** 一个 `batch` 扫描实验,第一遍测出「自旋锁快 34.8%」
(和材料里报的 25% 同量级,方向也对得上,读起来非常顺),第二遍只有
**+5.2%**。如果只跑一遍,那条结论就发出去了。

第二遍还顺带暴露了原因:第一遍那个 +34.8% 建立在**地板**上 ——
自旋锁那一侧在 `batch >= 4` 时所有读数都是 0.135–0.139 ms,不随参数
变化,说明任务代价被每轮固定开销盖住了,这一侧本来就不该拿来比。

**写法要求:**

- 同一个脚本、同一个节点、隔一段时间跑第二遍(不是同一遍里跑两次)
- 两遍都列进正文。**幅度不一致就写区间,不要写单值**
- **如果两遍方向不一致,那一项就没有结论**,写「未测到」而不是挑一遍
- 第二遍的原始日志要一起进仓库。它是证据,不是附件

**判据(和 5.5 节配合用):**

| 现象 | 说明 |
|---|---|
| 方向一致、幅度接近 | 可以给单值 |
| 方向一致、幅度差得多 | **只能给区间**,并写明不可复现 |
| 方向相反 | 这一项没有结论 |
| 某一侧读数不随参数变化 | 那一侧撞了地板,整行作废 |

### 5.8 验证脚本要断言「你写的那个数」,不是断言「你觉得对的那个数」

真实踩过的坑:正文里写「两遍的差值都是 405 µs」,而验证脚本里也写
`abs(d1 - 405) < 1.0`。跑出来 `158 µs / 388 µs`,红了。

原因是我在正文里就算错了(`1.227 - 1.069 = 0.158`,不是 `0.405`),
然后把这个错数**抄进了验证脚本**。这个断言的价值恰恰在于:它是独立
算出来的,所以能红。

**规矩:验证脚本里的期望值要来自原始数据或独立推导,不要从正文里抄。**
从正文抄期望值,等于用同一个错误源给自己盖章。

## 6 「X 到今天」对照节(每篇都要有)

材料如果是若干年前的,结尾要有时间对照节。规矩:

- **每条现状都要给官方主源的链接**(厂商文档、release notes、仓库)。
  不给链接的现状不要写
- **区分「确认」和「没确认」。** 抓不到原文、只拿到二手转述的,标
  「没确认」并说明为什么(页面截断、无法访问)。不要用「据称」糊过去
- **不要写没有主源的断言。** 真实踩过的坑:想写「某个工具于某年由某工具
  改名而来」,查下来官方没有版本历史页,**那就删掉不写**
- 工具对照表要包含「**已消失**」的工具,不能只列还活着的
- 不要在正文里写工具的具体子命令名,除非它真的在当前文档里 ——
  CLI 会改名(例:`nv-nsight-cu-cli` → `ncu`)。**以自己实际跑通的为准**

## 7 四道门(写完必须全绿)

```bash
REPO=~/projects/linear3735.github.io
SLUG=nsight-bogus-copies
DATE=20261114

# 结构门:front matter、标题、目录锚点、围栏语言/数量、图片是否存在
python3 $REPO/assets/blog/_tools/verify_post.py _posts/<date>-<slug>.md

# 代码门:抽正文的 python/cpp 块真跑 + 核对每个数字
python3 $REPO/assets/blog/$SLUG-$DATE/verify_code.py

# 图门:每张 SVG 能解析、有文字、继承页面字体
python3 $REPO/assets/blog/_tools/verify_svg.py assets/img/$SLUG-$DATE/*.svg

# 系列门:正文结构 + 代码门 + 合集页一致性,一次跑完
python3 $REPO/assets/blog/_tools/verify_series.py

# 合集页门:front matter、字段、统计数字、Liquid 真渲染
python3 $REPO/assets/blog/_tools/verify_hub.py
```

**门必须证明过它会红。** 写完一道门就跑一次「故意破坏」:改一个数字、
删一个字段、把 `{% endif %}` 拿掉,确认它 `exit=1` **并且报出你预期的
那条问题**,然后还原。没红过的门等于没有门——下面两个洞都是这么发现的。

### 合集页门踩过的坑

`verify_hub.py` 有两个独立的半边,缺一不可:

- **算术半边**:从 JSON 在 Python 里重算「已放出 / 待写 / 总数 / 百分比」,
  和渲染出来的 HTML 对。`divided_by` 是**整除**,`2/12` 是 `16%` 不是
  `16.7%`;写错了页面照样 200,只是数字不真
- **渲染半边**:有 ruby + liquid 就**真 parse + render**(`strict_variables`),
  引用不存在的顶层变量会硬报错。没有 ruby 时**要出声说 SKIP**,不能静默降级

**`strict_variables` 抓不住字段名拼错。** Liquid 把缺失的 *hash key* 解析成
nil,渲染成空字符串,只有顶层变量缺失才报错。所以 `{{ it.descr }}` 拼错会
产出一个结构完美、但少了一行字的页面。这一条是实测的:那个变异让
`verify_hub.py` 一直绿着,直到加了按 hub 声明的字段表才抓住。

**不要靠解析 Liquid 模板去推断「哪个字段是必填的」。** 我试了两版,两版都错:

1. 开标签正则写成 `\{%-?\s*if\s+it\.status...`,**永远匹配不到
   `{% elsif it.status...`**——`{%` 后面是 `els`,`if` 根本不在那个位置。
   于是每个 `elsif` 分支都是隐形的
2. 「先找开标签再各自找结尾」的写法,只要分支里有嵌套 `{% if %}` 就算错
   嵌套;而且没把 `{% for %}` 计进深度,状态链坐在深度 2,
   `depth == 1` 永远不成立,一个分支都识别不出来

**两版都是靠拿合成模板做自测才发现错的**,而且两次都是「静默判错」而不是
报错。结论:宁可手写一张字段表(`HUBS` 里的 `item_fields` /
`item_fields_by_status`)让它在数据缺字段时**大声报错**,也不要一个会在两个
方向上静默判错的启发式。

### 代码门的写法

**从文章里正则抽 ```` ```python ```` / ```` ```cpp ```` 块,不要手抄。**

坑(都是真实踩过的):

- **正文里的 ```` ```python ```` 块和它输出的 ```` ```text ```` 块,顺序不一定
  一致**(中间可能还夹着别的 `text` 块,比如文件树)。所以不能拿
  `text_blocks[i]` 去比第 `i` 个 python 块。要么按内容特征筛,要么在
  文章里保证顺序一致
- **抽出来的代码要不要补打印语句,得逐块决定。** 文章里贴可复用的函数
  (不打印)是好写法,那验证脚本就给它补一段尾巴;如果代码自己在正文里
  就打印了,就**不要再补**,否则会打两遍,对照必然失败
- 验证脚本要在**仓库根目录**下跑(正文代码里的路径是相对仓库根的)
- 比对输出要**逐字符相等**,不要 `.strip()` 掉再比。真实踩过的坑:
  `f"{'模式':>8}"` 和中文列名的宽度对不上,差几个空格,肉眼看不出来

### 图门的额外要求

`Check.run()` 的返回值必须累计后 `sys.exit(1 if sum(BAD) else 0)`
(见 `_tools/CONVENTIONS.md` 第 6 节,`exit(1 if BAD else 0)` 是错的)。

**生成后必须自己看一眼渲染结果:**

```bash
sips -s format png -Z 1400 x.svg --out /tmp/x.png   # 保持真实宽高比
```

时间线类图(横轴是时间)特别容易出问题的地方:标签放左边时画布宽度不够,
文字会跑出画布(`verify_svg.py` 查不到这一类,只有 `svgkit.Check` 能查到)。

## 8 交付报告格式

```
## <篇名>

文件:
  _posts/<file>.md            <N> 字
  assets/img/<dir>/           <N> 张 SVG
  assets/blog/<dir>/          <N> 个脚本 + <N> 个 CUDA 程序
  data/                       原始日志 <N> B + <N> 个 CSV

验证:
  结构门  exit 0
  代码门  exit 0  (<N> 个 python 块 + <N> 个 cpp 块;核对 <N> 个数字)
  图门    <N>/<N> 张已渲染检查
  系列门  exit 0  (含合集页一致性)
  合集页门 exit 0  (统计数字 + Liquid 真渲染)
  可证伪  各门都跑过负对照,<N>/<N> 例按预期变红
  复跑    第 <N> 次运行与第 1 次一致 / 不一致之处:<...>

  - <如实写,尤其:哪些倍数只在一台机器上测过、哪些材料的图看不到>
```

**「可证伪」这一行不能省。** 门全绿只说明它此刻没报错,不说明它有判断力。
每写完一道门就跑一遍负对照(故意破坏 → 确认它报出你预期的那条问题 →
还原),把结果写进来。

**「复跑」这一行是 GPU 系列特有的。** 性能数字受机器状态影响,能在同一
节点上再跑一遍并给出对比,是最低限度的稳健性证据。跑不了就写「未复跑」。
