## 1 这一站要解决的问题

前两站建立的是概念。这一站解决一个更实际的问题：**面对一个慢程序，你先看哪里？**

如果这个问题的答案是「先想想哪里可能慢」，那后面的优化就是猜。猜对了是运气，猜错了会花很久去优化一个根本不是瓶颈的地方 —— 而且优化完发现总时间没变，因为瓶颈在别处。

所以这一站的产出不是某个工具的操作方法，而是一条**顺序**：先看整体，再看局部；先定位，再解释。

## 2 两个工具分工不同，顺序不能反

| | Nsight Systems | Nsight Compute |
|---|---|---|
| 看什么 | 整体流水线、时间线 | 单个 kernel 内部 |
| 回答 | 时间花在哪、哪里有间隙、谁在等谁 | 这个 kernel 为什么慢 |
| 粒度 | 整个程序跨 kernel、跨 stream | 一个 kernel 的指标与 stall 原因 |
| 什么时候用 | 第一步 | 第二步，且只对已定位的 kernel |

顺序反了会怎样：一上来就用 Nsight Compute 分析某个 kernel，你大概率能拿到一堆指标和一个「瓶颈」判断，但**你不知道这个 kernel 值不值得优化** —— 也许它只占总时间的 3%，也许真正的问题是两个 kernel 之间那段谁都没在算的空隙。**前者优化到极限也只省 3%，后者根本不在 kernel 内部。**

这一站的建议入口，一个是 GTC 2026 的 Nsight Systems 讲座（讲整体流水线），一个是 NVIDIA 官方的 CUDA 开发者工具视频系列（补 Nsight Compute 的单 kernel 分析）。

## 3 时间线告诉你「哪有空隙」，不告诉你「为什么」

这是我写那篇实测文章时最直接的体会：时间线能精确告诉你**哪里有一段谁都没在算的时间**，但它不会告诉你那段空隙为什么存在。

空隙的可能来源，从时间线往下追是这几个方向：

- **等数据**：某个 kernel 在上游 kernel 或 memcpy 完成前无法开始；
- **等同步**：显式的同步点把并行度压平；
- **等调度**：block 数量与 SM 数量的关系不合适，出现尾部不均衡；
- **启动开销**：kernel 太短，启动和收尾的固定成本占比过高。

这四条里，前三条要去时间线上找依赖关系，第四条要看 kernel 的时长分布。**它们都不是「kernel 内部」的问题**，所以只做 Nsight Compute 是看不到的。

反过来，等你确认了「时间确实花在某个 kernel 内部」，才轮到 Nsight Compute 上场，去回答是算力受限、带宽受限，还是被 stall 卡住。

```text
定位顺序(不要跳步):
  1 Nsight Systems  -> 总时间花在哪? 有没有空隙?
  2 如果空隙是主因  -> 追依赖关系,不要进 kernel 内部
  3 如果某个 kernel 是主因 -> 才轮到 Nsight Compute
  4 改完再测一遍,确认总时间真的变了
```

第 4 步经常被省掉，但它是唯一能证伪「我以为我优化对了」的一步。

## 4 判断瓶颈的四个问题

把这一站压成四个问题，按顺序问：

1. **总时间里，GPU 在算的比例是多少？** 比例低就先查空隙，别查 kernel。
2. **空隙是谁造成的？** 看依赖：上游是谁、在等什么。
3. **被定位的那个 kernel，是算力受限还是带宽受限？** 这一步可以先估算再测：算一下它要搬多少字节、要算多少次，和硬件的带宽与算力比一下。估出来的量级和测出来的对不上，说明还有别的东西在拖。
4. **改完，总时间变了吗？** 没变就说明改的不是瓶颈 —— 这是信息，不是失败。

第 3 个问题里的「先估算再测」是关键。直接看 profiling 指标容易被一堆数字淹没；先自己算一个量级，再看实测，差异本身就是线索。
