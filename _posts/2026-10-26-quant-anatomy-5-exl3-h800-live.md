## 0 口径声明:这篇每一个数怎么量出来的

先把口径钉死,再谈数字(系列传统:口径比数字重要)。

- **被测对象**:4×H800 上的 EXL3 2.875bpw 聊天服务(1017 混合 EXL3 件,TP4 / DP1 / EP4,Graph + DSpark5,KV 用 FP8,max-num-seqs = 32)。就是第 ② 篇那份 188,245 键的件,服务形态跑起来了。
- **请求与计时循环:直接复用原作者的那套**——聊天请求、上下文目标 1500 token、thinking=false、temperature 0 / top_p 1、固定 seed、输出上限 768 token、自然结束;每请求独立 nonce / cache_salt 做冷前缀,不清服务缓存。测的就是"作者在 Blackwell 上测的同一道题"。
- **计时路径**:客户端在 Mac 上,经 SSH 隧道访问服务。所以本表吞吐与延迟**含完整用户入口路径**(网络与请求等待都算在内),不是节点内掐表。这条的差别在第 3 节有实数示教。
- **吞吐定义**:每档三次,单次 = 全部成功请求的输出 token 总和 ÷ 完整请求 makespan;报三次的算术平均。延迟分位数用该档全部正式请求的 nearest-rank。
- **TPOT 定义**:沿用作者定义——首末内容 chunk 到达时间差 ÷ (输出 token 数 − 1)。注意 DSpark 一次 chunk 可能携带多个 token,这不是逐 token 间隔。
- **完整性**:所有请求保留,不删慢样本;零错误、零空答、零 768 截断,全部自然停止收尾;每档三轮的服务成功请求增量与请求数一一对应,prefix hit 增量为 0(冷前缀成立)。

## 1 五档实测:C1 到 C64

主表(三次总吞吐的算术平均,单位 tok/s;TTFT / TPOT 为 P50 / P95,毫秒):

| 客户端并发 | 三次均值 tok/s | 合并吞吐 tok/s | TTFT P50 / P95 | TPOT P50 / P95 | 正式请求数 |
|---|---:|---:|---:|---:|---:|
| C1 | **156.81** | 156.70 | 349.9 / 522.3 | 5.14 / 5.93 | 24 |
| C4 | **327.76** | 327.67 | 586.3 / 989.8 | 10.44 / 11.66 | 36 |
| C16 | **651.97** | 651.95 | 1021.2 / 2634.8 | 20.41 / 24.12 | 144 |
| C32 | **695.27** | 695.27 | 1473.8 / 5434.6 | 39.86 / 45.25 | 288 |
| C64 | **693.06** | 693.03 | 15336.9 / 18665.6 | 42.70 / 47.24 | 576 |

(C1/C4/C16/C64 为同一批次的四档,780 条正式请求 + 255 条预热;C32 为随后在同一 seq32 服务上的补测,288 条正式 + 96 条预热。C32 与其余三档测量时间不同,属于**描述性并发曲线**,不当作改配置的配对 A/B。)

每次原件(三次逐次值,tok/s):

| 并发 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---:|---:|---:|
| C1 | 151.57 | 162.63 | 156.22 |
| C4 | 319.67 | 329.59 | 334.02 |
| C16 | 652.80 | 641.40 | 661.72 |
| C32 | 701.39 | 691.35 | 693.07 |
| C64 | 695.57 | 696.79 | 686.83 |

每档输入均实际 1470 token;平均输出依次约 324.0 / 320.2 / 318.4 / 314.5 / 316.2 token(C1→C64)。

一个必须先认的边界(诚实声明,原文照录级别):**C64 ≠ 引擎同时执行 64 条序列**。引擎 max-num-seqs=32,所以 C64 这一档的 makespan 与 TTFT 里有相当分量是 32 序列上限下的排队时间——这正是 TTFT P50 从 C32 的 1.47s 跳到 C64 的 15.34s 的原因。它如实反映的是"用户打 64 并发进来时的入口体验",不是引擎内部并发度。

## 2 与作者 Blackwell 数的对照:+24.6% / +54.1% / +53.8% 怎么读

第 ② 篇 §6 引过作者第一手(4×RTX PRO 6000 Blackwell 96GB,**共享多租户**,同一请求与计时循环):

| 并发 | 作者(Blackwell 共享) | 本团队(H800 独占) | 比值(算术) |
|---|---:|---:|---:|
| C1 | 125.861 | 156.81 | +24.6% |
| C16 | 423.110 | 651.97 | +54.1% |
| C32 | 452.16 | 695.27 | +53.8% |

同一套请求循环、同一口径计时,所以这张对照在"请求语义"上是干净的。但三条边界一条都不能省:

1. **共享 vs 独占**:作者数是共享多租户环境测的,我们是独占 4 卡。环境噪声会把我们的数推高多少,无法从这次测量分离。
2. **硬件不是同代**:H800 与 RTX PRO 6000 Blackwell 96GB 的算力/带宽/显存配置都不同。这不是"同一硬件上的引擎对比",不能反推引擎优劣。
3. **计时路径不同**(第 3 节):我们的数**含** SSH 隧道网络,作者数的测量路径按作者卡面原文。如果有什么偏向,这一层偏向是把我们的数往低拉的。

所以正确的读法是:**独占 4×H800 跑这份 EXL3 件,同一聊天负载下,吞吐已经达到并超过作者共享 Blackwell 报告的同一口径数字**——量级确认、形状确认(C16→C32 见顶),但不构成"我们的栈比作者的栈快 xx%"的算式。

## 3 计时路径课:节点内 169.39 vs 用户入口 156.81

本次测量前一晚,本团队对同一条服务线做过一组**节点内直连计时**的配对实测(同权重、同协议,配对 A/B 的 B 臂,三腿均值):

```
节点内直连计时:   C1 169.39 tok/s   C16 655.81 tok/s
本表(Mac→SSH 隧道): C1 156.81 tok/s   C16 651.97 tok/s
差:              C1 −7.4%          C16 −0.6%
```

这两个口径都保留,且不互相冒充。它顺手给了一个可复用的经验刻度:**在你这种远端服务形态下,经 SSH 隧道的用户入口计时对长连接多并发吞吐(C16)几乎无损(~0.6%),但对 C1 单请求约 −7.4%**——单请求下逐 chunk 的网络与转发开销占比大,聚合上去了就被摊薄。以后凡是报"用户入口数",记得这个 7% 量级;凡是报"引擎内数",记得强调它缺了入口段。

## 4 曲线形状读什么:平台点与排队点

把五档吞吐画出来,形状比绝对值更有信息量(均值点):

```
吞吐 tok/s
700 ┤                        ••695.27(C32)   ••693.06(C64)
    │
650 ┤            •651.97(C16)
    │
350 ┤    •327.76(C4)
    │
160 ┤•156.81(C1)
    +──────────────────────────────
      C1      C4      C16     C32     C64
```

- **C16 → C32:+6.6%**(算术:695.27/651.97 − 1)。还没撞上引擎天花板——序列上限 32 这一档,其实恰好是吞吐平台起点。
- **C32 → C64:−0.3%**(算术:693.06/695.27 − 1),持平。引擎不再加速,加入的只是队列;代价全部显现在 TTFT 上(P50 1.47s → 15.34s,TP50 段 10 倍)。
- **TPOT 随并发**:5.14 → 10.44 → 20.41 → 39.86 → 42.70 ms。C16 对应的 ~20ms 单 token 间隔 ≈ 单路视图 ~49 tok/s(算术:1000/20.41),对交互聊天属于顺;C32 起每路 ~25 tok/s,开始"看得出在等"。

量级结论:**这份 EXL3 件在 4×H800 上的"甜点"在 C16–C32(聚合 652–695 tok/s);再往上加并发,是排队不是加速**。这与第 ④ 篇 §1 行 B(原生 Q2 栈 C32 聚合 825.89)的位置相反——行 B 是 32 路聚合仍在爬坡,行 C 在 C32 见顶;两边负载协议不同(行 B:固定 128 输出短答;本篇:1500 上下文 + 上限 768 聊天),只能比形状不能比优劣。

## 5 当前服务配置(测的就是它)

- EXL3 2.875bpw 混合件(第 ② 篇的 188,245 键,1017 版)+ 4×H800,TP4 / DP1 / EP4
- Graph + DSpark5 草稿、KV 用 FP8、上下文池 300k、max-num-seqs=32、批 token 上限 4096
- 本次测量不改权重、不改服务配置、不重启服务;结束时客户端退出码 0,全部 1068 条正式请求零错误/零空答/零截断
- 这与第 ② 篇 §5 的两个世界说的一致:expert GEMM 行数远超 144 ⇒ 每个专家前向都走"dense 重构 + 常规 GEMM"路;prefill 与 decode 的 kernel 分解属本篇范围之外,trace 采集已另行立项,出结果后不混回本篇数据

## 6 诚实栏:这篇不谈什么

- **质量**:同权重两臂(eager/无 DSpark vs 当前 Graph/DSpark5)的 MMLU-1000 固定子集对照作业已按规提交,**正在集群排队,零分数**。在出分并完成独立复算之前,本系列对这份件不发表任何质量/精度数值——PPL、MMLU、"≤2% 质量差"都等那一轮。这延续篇 ② 的边界:性能数与质量数不强制同文。
- **C8**:本次档位取 C1/C4/C16/C32/C64,没有 C8。不做插值当实测。
- **历史优化收益**:本篇是当前服务的端到端描述,不是与任何历史节点的配对 A/B,不计算"快了多少倍"的旧账。
- **seq64**:max-num-seqs=64 的替代服务在备,未测、不外推;本篇 C64 的资格边界见 §1。
- **每卡 VRAM 快照**:沿用第 ④ 篇的 per-card 算术(≈48.8 GB/卡,EP4),运行时快照仍列在缺口清单。
