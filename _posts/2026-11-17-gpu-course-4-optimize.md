## 1 这一站要解决的问题

前 3 站解决了「为什么这样运行」和「瓶颈在哪」。这一站换一个问题：**看到一个优化手法，怎么判断它值不值得学？**

我的判断标准是：**它有没有把「改之前多少、改之后多少、为什么」三样都写出来。**

只给结论的材料（「用 double buffering 可以提升性能」）没法验证，也没法迁移 —— 你不知道它省的是哪一段、在什么形状下成立、什么时候反而更慢。而把每一步的代码和数字都留下的材料，你可以照着复现，也可以在复现不出来时知道是哪一步对不上。

这一站推荐的三份材料，价值都在这一点上。

## 2 Boehm 的 SGEMM：每一步都留了证据

原文 2022 年 12 月发表于 siboehm.com，配套源码在 GitHub。它的形式是：一个朴素实现出发，每改一步就给代码、给解释、给性能对照。这正是第 1 节说的那种材料。

**硬件和范围，先说清楚：** 它用 **A6000、FP32、CUDA core**，**没有用 Tensor Core**。所以它教的是「怎么一步步把 CUDA core 的矩阵乘逼到接近 cuBLAS」，不是 Tensor Core 的用法。想学后者要接第 5 站的 CUTLASS 材料。

**我把 README 的性能表逐行核了一遍**，因为「原文讲了多少步」这件事容易被转述错：

| README 表里展示的 | GFLOPs/s | 相对 cuBLAS |
|---|---|---|
| 1: Naive | 309.0 | 1.3% |
| 2: GMEM Coalescing | 1986.5 | 8.5% |
| 3: SMEM Caching | 2980.3 | 12.8% |
| 4: 1D Blocktiling | 8474.7 | 36.5% |
| 5: 2D Blocktiling | 15971.7 | 68.7% |
| 7: Avoid Bank Conflicts (Linearize) | 16213.4 | 69.7% |
| 8: Avoid Bank Conflicts (Offset) | 16459.2 | 70.8% |
| 11: Double Buffering | 17278.3 | 74.3% |
| 6: Vectorized Mem Access | 18237.3 | 78.4% |
| 9: Autotuning | 19721.0 | 84.8% |
| 10: Warptiling | 21779.3 | 93.7% |
| 0: cuBLAS | 23249.6 | 100.0% |

两条我要专门写出来，因为**不写就会被误传**：

1. **性能表展示到 11 号，没有 12 号。** 我核了仓库的 `src/kernels/`，`1..12` 号文件**都在**，其中 11 和 12 都是 double buffering 的实现；但 **README 的性能表里只有 11，12 没进表**。所以不能说「原文完整讲了 12 步」。
2. **表里的顺序不是编号顺序。** 第 6 号（Vectorized Mem Access，78.4%）排在 11 号（74.3%）后面，10 号（Warptiling，93.7%）排在最后。表是按性能排的，不是按教学顺序排的。照着编号顺序读代码，和照着表格顺序读结论，是两条不同的路径。

这份表本身也是这一站最好的教材：**从 1.3% 到 93.7%，中间每一步的收益都能看见，而且有几步收益很小（7 → 8 只从 69.7% 到 70.8%）。** 收益小的步骤同样值得看 —— 它们告诉你哪些改动是必要的但回报有限。

```text
读这份材料的顺序建议:
  原文    -> 按编号 1,2,3... 读,那是作者的推导顺序
  仓库    -> src/kernels/N_kernel_<名字>.cuh,编号与原文对应
  性能表  -> 按性能排的,和编号顺序不同,别当成步骤顺序
  注意    -> 表里没有 12 号
```

## 3 归约：Harris 那份经典，以及它过时的地方

Mark Harris 的归约材料是 2007 年的，38 页，7 个递进版本，背景是 G80。它的价值和它的年代是两件独立的事：

**仍然有效的部分：** 从一个朴素实现出发，逐步暴露出分歧（divergence）、共享内存 bank 冲突、线程利用率不足这些问题，每一步都给出改进和理由。这个**推导结构**是稳定的，不随硬件换代失效 —— 今天你写归约，遇到的还是这几类问题。

**不能直接搬的部分：** 那份材料里的旧代码依赖 **warp 内部的隐式同步**。这在当年的硬件上能工作，但**在现代 GPU 上不能直接移植** —— 正确的写法是使用显式的 warp 级原语。这是一处必须更新的地方，照抄旧代码会得到错的结果，不只是慢。

NVIDIA 后来在 Kepler 那篇文章里更新了归约的实现方式，并有一篇专门讲 warp 级原语的博客。要写今天的归约，从那两篇入手，把 2007 那份当**思路教材**而不是代码样板。

```text
2007 那份材料怎么用:
  学  -> 优化的推导结构和每步暴露的问题
  别抄-> 依赖隐式 warp 同步的代码
  今天-> 显式 warp 级原语 + 更新过的归约实现
```

## 4 Triton：把同样的思路接到现代算子上

前面两份材料是 CUDA core 时代的。要把它接到今天真正在跑的算子（LayerNorm、Attention、Persistent Matmul）上，Triton 的官方教程是一条顺路：它的解释和可运行源码放在一起，而且它处理的是「一个 tile 怎么映射到线程和内存」这个抽象层 —— 恰好是第 2 站那些机制概念的直接延续。

它和 CUTLASS 的关系值得说清：Triton 让你用更高的抽象描述分块与并行，CUTLASS/CuTe 让你下到 layout 和 MMA 指令那一层。**先 Triton 后 CUTLASS** 是更省力的顺序，因为 Triton 会让你先建立「分块、复用、流水线」的直觉，再用这些直觉去读 CUTLASS 的模板参数。

## 5 怎么读这类材料

把这一站的判断标准收成一句可操作的话：**跟着数字走，别跟着结论走。**

具体做法是，每读到一步就问三个问题：

1. 这一步改之前是多少？（如果材料没给，说明它不值得学）
2. 改的是什么？（一个变量还是同时改了多个？同时改多个的话，收益不能归给其中任何一个）
3. 这个收益在什么形状、什么硬件下成立？（换一个形状还成立吗）

第 2 个问题特别重要：**一个性能对比如果在两个维度上都不同，它没有结论。**

## 6 我核到的、和我没核的

**核到了什么。** Boehm 原文与 GitHub 仓库、Harris 的 PDF、Kepler 那篇更新、warp 级原语那篇、Triton 教程目录，全部返回 200。其中 Boehm 这条我核到了**文件层面**：仓库默认分支是 `master`，`src/kernels/` 下 1–12 号文件齐全，11 和 12 都是 double buffering，README 性能表逐行抓取后确认只到 11 号。

**没核到什么。** 四条边界：

1. **我没有编译或运行这些 kernel。** 第 2 节的表格是 README 的数字，**不是我实测的**。我核的是「表里写了什么、仓库里有什么文件」，不是「这些数字在我的硬件上成不成立」。
2. **我没有逐页读那份 38 页 PDF。** 38 页、7 个版本这个结构是它的公开描述；「依赖隐式 warp 同步」这一处我是通过 NVIDIA 后续更新的材料确认需要更新的，没有逐行读完全部 7 个版本。
3. **原作者原文的步数与仓库编号的关系我没逐节核对。** 我确认了仓库有 1–12 号和性能表只到 11 号，没有逐节比对「原文第 N 节」与「仓库第 N 号文件」是否一一对应。
4. **Triton 教程我没有逐个跑。** 我核的是目录入口可达。
